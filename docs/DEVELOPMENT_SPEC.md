# 무한생(LIFE) — Codex 통합 개발 지시서 v1.0

## 0. 프로젝트 목표

GitHub Pages에 배포하고 티스토리 블로그에 iframe으로 삽입할 수 있는 선택형 웹게임 **「무한생」**을 개발한다.

### 게임 콘셉트

"이번 생에는 무엇으로 태어날까?"

플레이어는 인간에 한정되지 않는다. 동물, 식물, 기계, 사물, 바이러스, 인공지능, 던전, 천체 등 다양한 존재로 태어난다.

세계관 역시 현실에 한정되지 않는다. 게임·소설·영화에서 익숙한 장르를 바탕으로 한 독창적인 세계를 사용한다.

출생 위치, 타고난 특징, 치명적인 결함, 플레이어의 선택, 무작위 사건에 따라 예측 불가능한 인생을 경험한다.

**게임의 핵심 재미는 황당한 사건이 앞선 선택과 연결되면서 뜻밖의 인생 이야기가 만들어지는 것이다.**

단순한 능력치 올리기 게임을 만들지 않는다.

---

## 1. 최우선 개발 원칙

1. 게임 엔진과 콘텐츠를 완전히 분리한다.
2. 콘텐츠는 JSON, 이미지는 SVG 중심으로 관리한다.
3. 신규 세계관·존재·사건·선택지·분기·엔딩·이미지는 가능한 한 엔진 수정 없이 추가한다.
4. 콘텐츠 추가 및 수정은 Codex가 직접 수행한다.
5. 별도의 관리자 페이지나 시각적 콘텐츠 편집기는 만들지 않는다.
6. 기존에 정상 작동하는 기능을 임의로 변경하거나 삭제하지 않는다.
7. 기획에 없는 기능을 임의로 추가하지 않는다.
8. 복잡한 프레임워크나 불필요한 외부 의존성 도입을 피한다.
9. 게임은 반드시 처음부터 엔딩까지 정상 진행되어야 한다.
10. 디자인보다 게임 진행, 분기, 저장, 콘텐츠 확장의 안정성을 먼저 완성한다.

기존 저장소에 코드가 있다면 먼저 구조를 확인하고 재사용한다. 요청하지 않은 전체 재작성은 금지한다.

## 2. 개발 환경

- 언어: TypeScript
- 빌드: Vite
- 화면: HTML + CSS
- 콘텐츠: JSON
- 이미지: SVG 우선, WebP 보조
- 저장: localStorage
- 테스트: Vitest
- 배포: GitHub Pages
- 블로그 연동: 티스토리 iframe
- 모바일 우선 반응형 디자인
- 서버 및 데이터베이스 없음
- 회원가입 없음
- 실시간 AI 스토리 생성 없음

Vite의 `base` 설정을 GitHub Pages 프로젝트 경로에 맞게 처리한다.

모든 콘텐츠 및 이미지 경로는 배포 경로를 고려해 해석한다. 루트 절대경로를 하드코딩하지 않는다.

GitHub Pages 직접 접속과 티스토리 iframe 실행 모두 지원한다.

## 3. MVP 개발 범위

### 세계관 6종

1. 중세 판타지
2. 좀비 아포칼립스
3. 사이버펑크
4. 우주 SF
5. 현대 헌터물
6. 현실 세계

유명 작품의 장르적 특징만 참고한다. 타 작품의 고유 캐릭터, 지명, 이미지, 설정을 무단 복제하지 않는다.

### 콘텐츠 최소 수량

- 세계관: 6개
- 출생 유형: 30개
- 출생 유형별 위치: 최소 2개
- 출생 유형별 특징: 최소 2개
- 출생 유형별 결함: 최소 2개
- 세계관별 공통 사건: 12개 × 6 = 72개
- 존재별 전용 사건: 3개 × 30 = 90개
- 범용 돌발 사건: 18개
- 사건 총합: 180개
- 엔딩: 세계관당 5개, 총 30개
- 사건별 선택지: 2~3개

사건 180개는 플레이 한 번에 전부 등장하는 것이 아니다. 세계관, 존재, 상태, 조건, 선택에 따라 일부가 등장한다.

숫자만 바뀌는 형식적인 사건으로 수량을 채우지 않는다.

## 4. 출생 시스템

게임을 시작하면 다음 순서로 운명을 생성한다.

1. 세계관 추첨
2. 존재 유형 추첨
3. 출생 위치 추첨
4. 타고난 특징 추첨
5. 치명적인 결함 추첨
6. 숨겨진 운명 지정
7. 출생 이야기 생성

출생 위치·특징·결함은 존재별 JSON 데이터에서 가중치 기반으로 선택한다.

숨겨진 운명은 시작 시 내용을 공개하지 않고 특정 사건에서 드러나게 한다.

출생 조건이 단순한 문구에 그쳐서는 안 된다.

예를 들어 다음과 같이 게임에 영향을 주어야 한다.

- 왕실 무기고에서 태어난 마검 → 왕족·기사 관련 사건 등장
- 고대 유적에서 태어난 마검 → 고대 마법 사건 등장
- 말하는 검 → 대화 선택지 등장
- 저주받은 검 → 저주 관련 사건 발생
- 주인 의존 결함 → 주인을 잃으면 위기 발생

출생 조건이 서로 모순되는 조합은 데이터 조건으로 차단한다.

다만 황당한 조합 자체는 허용한다. 세계관 내부에서 설명 가능한 이유가 있다면 적극적으로 활용한다.

### 재추첨

MVP에서는 게임 시작 전 전체 운명 재추첨을 무제한 허용한다.

부분 잠금·부분 재추첨은 구현하지 않는다.

게임 시작 후에는 출생 조건을 변경할 수 없다.

## 5. 생애 진행 시스템

인간의 나이를 공통 기준으로 사용하지 않는다.

대신 모든 존재가 공유하는 생애 단계 시스템을 사용한다.

1. 탄생
2. 각성
3. 성장
4. 위기
5. 전환
6. 절정
7. 결말

한 번의 플레이는 기본적으로 사건 12개와 최종 엔딩 1개로 구성한다.

목표 플레이 시간은 약 4~7분이다.

인간은 성장과 노화를 경험할 수 있지만, 사물·기계·바이러스·행성 등은 해당 존재에 맞는 시간과 변화로 표현한다.

시간 단위는 콘텐츠에서 정의하며 실제 년수와 일치시킬 필요가 없다.

### 생애 변화 예시

**인간**
탄생 → 성장 → 취업 → 위기 → 성공 또는 몰락

**마검**
제작 → 각성 → 주인 만남 → 전쟁 → 전설 또는 파괴

**바이러스**
발생 → 전파 → 변이 → 치료제 등장 → 소멸 또는 진화

**자판기**
제조 → 설치 → 자아 각성 → 인간과 충돌 → 해방 또는 폐기

**블랙홀**
탄생 → 성장 → 주변 천체 흡수 → 우주적 사건 → 소멸 또는 초월

플레이 도중 다른 존재로 변신하는 것도 허용한다.

예: 슬라임 → 드래곤 / 자판기 → AI / 마검 → 인간

변신 전의 사건 기록과 상태는 유지한다.

## 6. 능력치 시스템

공통 능력치는 5개로 고정한다.

- `survival`: 생존력
- `influence`: 영향력
- `intelligence`: 지능
- `freedom`: 자유도
- `chaos`: 혼돈도

모든 능력치는 0~100 범위다.

출생 조건과 선택 결과에 따라 변화한다.

### 혼돈도

혼돈도는 게임의 핵심 능력치다.

혼돈도가 높으면 황당한 사건과 희귀 사건이 나타날 가능성이 높아진다.

단, 혼돈도는 성공 확률이나 보상을 무조건 높이는 능력치가 아니다.

높은 혼돈도는 특별한 기회와 심각한 위험을 함께 제공한다.

### 공통 상태

게임 상태는 최소한 다음을 포함한다.

- 난수 시드
- 현재 세계관 ID
- 현재 존재 ID
- 출생 위치 ID
- 특징 ID
- 결함 ID
- 숨겨진 운명 ID
- 현재 생애 단계
- 현재 사건 ID
- 능력치
- 태그
- 플래그
- 아이템
- 방문한 사건 목록
- 선택 기록
- 완료한 사건 수
- 콘텐츠 버전

## 7. 사건 및 분기 엔진

모든 사건은 JSON으로 정의한다.

사건에 필요한 필드:

- 고유 ID
- 세계관 ID
- 적용 존재 ID 또는 태그
- 생애 단계
- 제목
- 설명
- 이미지 경로
- 등장 가중치
- 발생 조건
- 선택지
- 선택 결과
- 다음 사건 ID

### 지원 조건

- 능력치 비교
- 특정 플래그 보유 여부
- 특정 태그 보유 여부
- 특정 아이템 보유 여부
- 세계관 일치
- 존재 유형 일치
- 이전 사건 또는 선택 이력

조건은 `all`, `any` 조합을 지원한다.

숫자 비교 연산자는 다음을 지원한다.

- `gte`
- `lte`
- `equals`
- `notEquals`

### 지원 효과

- `addStat`
- `setStat`
- `setFlag`
- `addTag`
- `removeTag`
- `addItem`
- `removeItem`
- `transformEntity`

효과와 조건은 선언형 JSON으로 정의한다.

임의 JavaScript 코드 실행이나 `eval`을 허용하지 않는다.

### 분기 방식

1. 지정 사건으로 직접 이동
2. 조건에 따라 다른 사건으로 이동
3. 조건에 맞는 사건을 가중치로 추첨

우선순위:

직접 지정 분기 → 조건부 분기 → 일반 사건 추첨 → 안전한 대체 사건

이미 등장한 사건은 기본적으로 반복하지 않는다.

존재하지 않는 사건 ID를 참조하면 콘텐츠 검증 단계에서 오류로 처리한다.

특정 조건으로 도달할 수 없는 분기는 테스트에서 감지한다.

무한 루프를 막기 위해 최대 사건 진행 횟수 및 방문 제한을 적용한다.

## 8. 콘텐츠 JSON 규격

콘텐츠 스키마 버전은 `schemaVersion: 1`로 시작한다.

### 세계관 예시

```json
{
  "schemaVersion": 1,
  "id": "fantasy",
  "name": "중세 판타지",
  "description": "검과 마법이 존재하는 세계",
  "image": "images/worlds/fantasy.svg",
  "entityIds": [
    "fantasy_adventurer",
    "fantasy_slime",
    "fantasy_dragon",
    "fantasy_sword",
    "fantasy_dungeon"
  ]
}
```

```json
{
  "schemaVersion": 1,
  "id": "legendary_weapon",
  "worldIds": ["fantasy"],
  "title": "전설이 된 마검",
  "description": "수천 년 후에도 당신의 이름이 전해진다.",

```

모든 JSON은 동일한 스키마 규칙을 따른다.

위 예시를 기준으로 타입과 검증기를 작성하되, 실제 플레이에 필요한 필수 필드는 누락 없이 정의한다.

사건의 전용성은 `entityIds`, 태그, 조건으로 판별한다.

선택지의 직접 분기 목적지는 실제 데이터에 존재해야 한다.

데이터를 임의로 읽고 추측하는 방식이 아니라 엄격한 타입 검증 후 로딩한다.

---

## 9. 엔딩 시스템

엔딩은 세계관당 5종, 총 30종을 구현한다.

다음 유형을 참고하되 세계관에 맞게 변형한다.

- 평범한 생존
- 전설적 성공
- 파멸과 소멸
- 예상 밖의 인생 역전
- 세계를 뒤흔든 존재

단순히 점수 총합으로 엔딩을 결정하지 않는다.

능력치, 과거 선택, 상태 플래그, 존재 유형을 함께 반영한다.

엔딩이 여러 개 충족되면 우선순위로 결정하고, 동률일 경우 ID 기준으로 일관되게 선택한다.

어떤 조건에서도 최종 엔딩이 없는 상태가 발생하지 않도록 세계관별 기본 엔딩을 제공한다.

결과 화면에는 다음을 표시한다.

- 최종 존재
- 태어난 세계관
- 출생 조건
- 최종 능력치
- 주요 사건 타임라인
- 최종 엔딩 이름
- 엔딩 설명
- 다시 태어나기 버튼

## 10. SVG 이미지 시스템

게임 이미지의 기본 형식은 SVG다.

다음 항목을 SVG로 제작한다.

- 세계관 대표 이미지 6개
- 존재 대표 이미지 30개
- 사건 이미지 (재사용 가능한 장면 포함)
- 엔딩 대표 이미지
- UI 아이콘

모든 사건마다 별도 SVG를 의무적으로 생성할 필요는 없다. 세계관·존재·상황에 맞는 이미지를 재사용할 수 있어야 한다.

이미지는 콘텐츠 JSON의 상대 경로로 지정한다.

SVG는 모바일과 PC에서 선명하게 표시되도록 `viewBox`를 사용한다.

외부 SVG의 스크립트 및 외부 참조는 허용하지 않는다.

이미지가 없거나 로딩에 실패하면 기본 대체 이미지로 표시한다.

복잡한 배경 일러스트는 WebP도 허용한다.

**이미지 제작에 과도한 시간을 쓰지 않는다.**

처음에는 일관된 단순 벡터 스타일로 완성하고, 추후 교체 가능하도록 한다.

개인정보는 저장하지 않는다.

## 15. AGENTS.md 작업 보호 규칙

프로젝트 루트에 `AGENTS.md`를 생성하고 다음 규칙을 작성한다.

### 작업 범위 보호

- 요청된 파일과 관련 영역만 수정한다.
- 단순 콘텐츠 추가를 위해 엔진 코드를 변경하지 않는다.
- 기존 기능의 삭제, 이름 변경, 동작 변경은 명시적 승인 없이 금지한다.
- 요청하지 않은 리팩터링을 수행하지 않는다.
- 새로운 라이브러리를 임의로 추가하지 않는다.
- 기존 데이터 규격을 임의로 변경하지 않는다.
- 기존 파일 전체를 불필요하게 재작성하지 않는다.

### 콘텐츠 추가 규칙

세계관 추가, 존재 추가, 사건 추가, 이미지 추가 작업에서는 우선 콘텐츠 파일만 수정한다.

현재 엔진으로 구현할 수 없는 규칙이 필요하면 우회해서 기존 코드를 망가뜨리지 말고 제한사항을 보고한다.

콘텐츠 ID는 기존 규칙을 유지한다.

기존 콘텐츠와 충돌하거나 중복되는 파일을 생성하지 않는다.

### 검증 규칙

변경 후 반드시 다음을 실행한다.

```bash
npm run validate:content
npm run test
npm run build
```

실패한 항목은 수정 후 다시 검증한다.

테스트를 통과시키기 위해 테스트를 삭제하거나 검사 조건을 완화하지 않는다.

### 작업 기록

프로젝트에 `CHANGELOG.md`와 `docs/PROJECT_STATE.md`를 유지한다.

작업을 마칠 때 다음 정보를 짧게 기록한다.

- 추가·수정한 기능
- 변경된 파일
- 추가된 콘텐츠 수량
- 테스트 결과
- 알려진 문제
- 다음 작업 시 주의사항

장시간 작업이나 대화 컨텍스트가 길어졌을 때는 프로젝트 파일의 현재 상태를 확인하고 이어서 작업한다.

이전 대화 기억에만 의존해 구조를 추측하지 않는다.

### 삽질 방지

- 현재 작업과 무관한 개선을 시작하지 않는다.
- 불필요한 구조 변경을 하지 않는다.
- 동일한 오류 해결을 반복할 경우 원인을 분석하고 접근 방식을 변경한다.
- 임시방편으로 오류를 숨기지 않는다.
- 검증되지 않은 성공을 보고하지 않는다.
- 완료된 기능을 다시 개발하지 않는다.

## 18. 이번 작업의 진행 지시

이 명세서를 기준으로 개발을 진행한다.

다만 모든 기능과 콘텐츠를 한 번에 작성하지 않는다.

먼저 저장소 구조를 확인한다.

그다음 `AGENTS.md`, `docs/PROJECT_STATE.md`, JSON 스키마, 게임 엔진의 기본 구조를 구축한다.

Phase 1이 완료되면 검증 결과와 변경 파일을 보고한다.

**명시적인 후속 지시 없이 Phase 2~5를 자동으로 연속 진행하지 않는다.**

기획의 세부 사항이 부족하더라도 기존 시스템을 크게 변경하는 결정을 독단적으로 내리지 않는다.

우선 기존 명세와 호환되는 최소한의 구조를 구현한다.

**최우선 목표는 화려한 코드가 아니라, 기존 기능을 보호하면서 콘텐츠를 계속 추가할 수 있는 안정적인 인생 시뮬레이션 엔진이다.**
